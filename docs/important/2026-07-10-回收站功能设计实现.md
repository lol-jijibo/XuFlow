# 回收站功能 — 设计文档

**日期**：2026-07-10  
**版本**：v1.0  
**状态**：✅ 已实现

---

## 1. 背景与动机

AI 对话工具的一次会话可能包含数小时的思考、代码产出和决策过程。误删会话是不可逆的数据损失。传统的"删除即物理删除"模式对用户不够友好。

### 设计目标

| 目标 | 说明 |
|---|---|
| **防止误删** | 删除操作默认进入回收站，而非物理删除 |
| **可恢复** | 用户可从回收站恢复已删除的会话到原项目 |
| **可彻底删除** | 用户可选择彻底删除（物理清除，不可恢复） |
| **自动清理** | 超过 30 天的回收站记录自动清理，避免数据库膨胀 |
| **低侵入** | 基于现有 SQLite 结构做最小增量改动 |

## 3. 数据库设计

### 3.1 表结构变更

在现有 `sessions` 表上增加一个字段：

```sql
ALTER TABLE sessions ADD COLUMN deleted_at INTEGER;
-- NULL = 正常会话
-- 非 NULL = 在回收站中，值为删除时的毫秒时间戳
```

### 3.2 增量迁移

`SessionStore::run_migrations()` 在应用启动时自动检测并执行，不破坏已有数据：

```rust
/// 增量迁移：为已有数据库添加新字段，不破坏现有数据。
fn run_migrations(conn: &Connection) -> Result<()> {
    let has_deleted_at: bool = conn
        .prepare("SELECT deleted_at FROM sessions LIMIT 0")
        .is_ok();
    if !has_deleted_at {
        conn.execute_batch(
            "ALTER TABLE sessions ADD COLUMN deleted_at INTEGER;",
        )?;
    }
    Ok(())
}
```

### 3.3 查询过滤

所有正常列表查询自动排除回收站中的会话：

```sql
-- 之前：返回所有会话
SELECT ... FROM sessions WHERE project_id = ? ORDER BY updated_at DESC

-- 之后：只返回未删除的会话
SELECT ... FROM sessions WHERE project_id = ? AND deleted_at IS NULL ORDER BY updated_at DESC
```

## 4. 操作语义

| 操作 | 前端方法 | 后端命令 | SQL 操作 | 可逆 |
|---|---|---|---|---|
| **移入回收站** | `deleteConversation` | `db_delete_session` | `UPDATE sessions SET deleted_at = now()` | ✅ |
| **恢复** | `restoreConversation` | `db_restore_session` | `UPDATE sessions SET deleted_at = NULL` | ✅ |
| **彻底删除** | `permanentDeleteConversation` | `db_permanent_delete_session` | `DELETE FROM sessions WHERE id = ?` | ❌ |
| **查看回收站** | `trashConversations` | `db_list_trash_sessions` | `SELECT ... WHERE deleted_at IS NOT NULL` | — |
| **自动清理** | 启动时自动 | `purge_expired_internal` | `DELETE WHERE deleted_at < cutoff` | ❌ |

### 4.1 移入回收站

- 前端从 `projects` 数组移除会话
- 后端设置 `deleted_at = ts_now()`
- 前端同步添加到 `trashConversations` 数组
- **消息数据完整保留**，不执行任何清理

### 4.2 恢复

- 前端从 `trashConversations` 数组移除
- 后端清除 `deleted_at = NULL`
- 前端同步恢复到对应项目的 `conversations` 数组
- 会话标题、消息等完整数据恢复

### 4.3 彻底删除

- 前端从 `trashConversations` 数组移除
- 后端执行 `DELETE FROM sessions WHERE id = ?`
- 由 `ON DELETE CASCADE` 外键约束自动清理关联的 `messages` 数据
- **此操作不可逆**

### 4.4 自动清理

- 应用启动时自动检查：删除超过 30 天的回收站记录
- 记录数量 > 0 时输出日志：`[xuflow] 启动时清理了 N 条过期回收站记录`
- 用户也可通过"清空回收站"按钮手动触发（等效于 retention_days = 0）

## 6. UI 设计细节

### 6.1 回收站区域位置

位于侧边栏项目列表下方、设置按钮上方，始终可见（不随项目滚动）。

### 6.2 交互行为

| 交互 | 触发 | 行为 |
|---|---|---|
| 点击"回收站"行 | 单击 | 展开/折叠回收站列表 |
| 悬停已删除会话 | hover | 显示 [恢复] [彻底删除] 按钮 |
| 点击恢复按钮 | 单击 | 会话恢复到原项目，项目自动展开 |
| 点击彻底删除按钮 | 单击 | 物理删除，不可恢复 |
| 点击清空按钮 | 单击 | 清空所有回收站记录 |

### 6.3 视觉状态

- **正常会话**：标准标题样式（黑色/白色文字）
- **已删除会话**：灰色文字 + 删除线（`text-decoration: line-through`）
- **回收站计数**：胶囊形状徽章，灰色底
- **"清空"按钮**：hover 时变红色警示
- **"彻底删除"按钮**：hover 时变红色

## 7. 数据生命周期

```
创建会话 ──→ 正常使用 ──→ 软删除 (deleted_at=now)
                              │
                    ┌─────────┴──────────┐
                    ↓                    ↓
              恢复 (恢复原状)      超过 30 天 → 自动物理删除
                    │                    ↑
                    │              用户手动彻底删除
                    ↓
              正常使用
```

## 8. 向后兼容

- **旧数据库**：首次启动时自动执行 `ALTER TABLE ADD COLUMN`，旧数据 `deleted_at` 为 `NULL`（正常状态）
- **旧前端调用**：`db_delete_session` 行为从物理删除变为软删除，但参数和返回值不变
- **localStorage**：回收站数据不同步到 localStorage，仅存于 SQLite（localStorage 仅作紧急回退）

---

## 9. 注意事项

1. **软删除不清理消息**：消息数据完整保留在 `messages` 表中，确保恢复后对话历史完整
2. **项目删除 vs 会话软删除**：项目删除（`db_delete_project`）仍为物理删除，会级联删除该项目下所有会话（包括回收站中的）
3. **30 天清理时机**：仅在应用启动时执行，不在后台定时执行——启动频率足够日常使用
4. **性能影响**：仅新增一个可为 `NULL` 的索引列，对正常查询零影响（`deleted_at IS NULL` 可利用索引）
